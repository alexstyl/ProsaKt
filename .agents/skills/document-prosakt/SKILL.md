# Document Prosa.kt

Every time a new concept is introduced, it must be documented as part of the same change. Cover new user-facing DSL capabilities and behavior in the API guides; generated API signatures alone do not explain a concept. When a guide introduces an unfamiliar API or concept, explain it at first use rather than leaving readers to infer its meaning from code.

## Sources and placement

- Read the relevant implementation in `src/commonMain/kotlin/com/alexstyl/prosakt/` and its tests in `src/commonTest/` and `src/jvmTest/` before describing behavior.
- API guides live in `website/src/content/docs/docs/`. Extend the closest existing API guide; add a page when the concept warrants its own explanation. New concepts belong in the API guides. The first-file tutorial is complete and outside this workflow.
- Use `classes.md`, `functions.md`, and `types.md` as the models for API guides.
- API reference HTML is generated by Dokka from Kotlin declarations and KDoc. Put API-level explanations and constraints in KDoc on the relevant public declarations when needed. Do not hand-edit `build/dokka/` or `website/public/api/`.
- The root `README.md` points readers to the website. Keep detailed usage documentation in the guides.

## Guide conventions

Use `.md` for API guides.

Match the existing frontmatter:

```yaml
---
title: Concept name
description: A short explanation of what the reader can generate or do.
sidebar:
  order: 18
---
```

Choose an order appropriate to neighboring pages. New pages also need an entry under `API guides` in the explicit sidebar in `website/astro.config.mjs`; frontmatter alone does not add them to that navigation.

Write task-oriented `##` headings such as “Add a parameter.” Under each heading:

1. Explain what the API does, which enclosing DSL block accepts it, and what its arguments or settings mean. Use the existing direct “Use `…` inside `…`” style.
2. Show a small, realistic fenced `kotlin` example. Include `import com.alexstyl.prosakt.ktFile` and `val source = ktFile { ... }` for standalone examples, plus other imports when required.
3. Follow the example with `Generated Kotlin:` and a fenced `kotlin` block showing the actual emitted source.
4. Explain relevant defaults, ordering, restrictions, or automatic behavior near the example. Link related guides using `/docs/<slug>/` and heading anchors where useful.

Introduce concepts incrementally. Explain supporting calls such as `type {}`, `reference()`, `literal()`, or `argument {}` when first used, or briefly identify their role and link an existing explanation. Keep examples focused on the concept being taught.

Distinguish the generator code from the generated Kotlin. Verify exact output, including imports, whitespace, and implicit behavior, against the implementation and tests. Prosa.kt returns source text; do not imply that it compiles code or writes files.

## Generated formats and verification

The site uses Astro with Starlight. `website/src/lib/docs-markdown.ts` and the page routes derive Markdown versions, `/llms.txt`, and `/llms-full.txt` from the guides. Edit the source guides, not these generated outputs. Keep explanations and code understandable in plain Markdown as well as HTML.

- Check new examples against relevant tests. When an example exercises new behavior, verify its emitted output with a focused Kotlin test; use the existing JVM compilation-test pattern when generated Kotlin validity needs proof.
- For guide or navigation changes, run `bun --bun run build` from `website/`. This generates the Dokka reference and builds the site, including Markdown exports. Inspect the affected output and links in `website/dist/`.
- When changing documentation generation code, run the relevant website tests (`bun run test` from `website/`) and `bun --bun run check` as appropriate.
- Review the final changes for unexplained concepts, stale examples, duplicate prose, broken links, and accidental generated files. Keep the documentation scoped to the changed concepts.
